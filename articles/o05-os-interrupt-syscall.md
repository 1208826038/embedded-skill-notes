# 操作系统进阶（五）· 中断、异常与系统调用

> 操作系统本体就是"被中断驱动"的程序。本文讲清硬件中断、CPU 异常、系统调用（陷入）三者的区别与共性，以及一次"用户态→内核态→用户态"的完整旅程：从硬件引脚、中断向量表/IDT、上下文保存、中断处理上下半部，到 `int 0x80`/`syscall` 指令陷入内核。内容大量呼应 `02-rtos-tuning.md` 第五、六、十章（Cortex-M 的 NVIC/SysTick/PendSV/SVC、临界区、FromISR 边界），把 MCU 的中断机制放进通用 OS 框架里。

---

## 一、三类"控制流转移"：中断 / 异常 / 系统调用

| 类型 | 来源 | 同步/异步 | 例子 |
| --- | --- | --- | --- |
| **中断（Interrupt）** | 外部硬件 | 异步 | 定时器到、网卡收包、按键 |
| **异常（Exception）** | CPU 执行指令时 | 同步 | 除零、缺页、非法指令、断点 |
| **系统调用（Syscall/Trap）** | 程序主动 `int`/`syscall` | 同步（自愿） | `read`/`write`/`fork` |

三者最终都走**同一套"陷入内核"机制**：硬件自动保存部分上下文、切换到内核栈、跳到预先注册的处理函数。区别只在"触发源"和"是否有意为之"。

---

## 二、硬件中断机制

### 2.1 从引脚到向量

外部设备通过**中断请求线（IRQ）** 拉高电平/边沿，经**中断控制器（如 x86 的 PIC/APIC、ARM 的 GIC、Cortex-M 的 NVIC）** 仲裁后，给 CPU 一个**中断号（向量号）**。CPU 据此查**中断向量表/IDT**，跳到对应 ISR。

> MCU 呼应（见 `02` 第五章）：Cortex-M 把中断向量表放在地址 0（或 `VTOR` 指向处），前 15 个是系统异常（含 `SVC #11`、`PendSV #14`、`SysTick #15`），之后是外部中断。NVIC 负责优先级仲裁、尾链（Tail-Chaining）、迟滞（Late-Arrival）——这些优化在通用 APIC/GIC 上同样有对应概念。

### 2.2 中断的生命周期

```
1. 设备拉 IRQ
2. 中断控制器仲裁（按优先级），向 CPU 发信号
3. CPU 完成当前指令，硬件自动：
   - 关中断（或压 EFLAGS 后清 IF）
   - 保存 PC、PSW 等到内核栈
   - 查向量表跳到 ISR 入口
4. ISR 执行（上半部，越快越好）
5. 发 EOI（End of Interrupt）通知控制器
6. 中断返回（IRET）：恢复上下文，开中断，回到被中断处
```

### 2.3 可屏蔽 vs 不可屏蔽

- **可屏蔽中断（INTR）**：可被 `CLI`/`IF` 关闭，普通设备中断。RTOS 的 `BASEPRI` 屏蔽部分优先级即此思想的精巧版（`02` 6.2）。
- **不可屏蔽中断（NMI）**：电源掉电、硬件错误等致命事件，关不掉，优先级最高。

## 三、异常（Exception）

同步发生于指令执行：
- **故障（Fault）**：执行前/中出错，**返回后可重新执行**（如缺页——修好页表后重跑那条指令，见 `o04` 5.2）。
- **陷阱（Trap）**：有意陷入，用于调试（`int3` 断点）或**系统调用**。
- **终止（Abort）**：致命错误（如硬件故障），无法恢复，通常直接崩溃。

---

## 四、系统调用：用户态如何"叫"内核

用户程序不能直接碰硬件/内核数据（特权隔离），要做事（如读文件）必须**请求内核代劳**。机制：

```
用户态程序
  → 把系统调用号放进约定寄存器（如 RAX），参数放其他寄存器
  → 执行 syscall 指令（或老式 int 0x80）
  → CPU 切到内核态，跳到 syscall 入口（内核预注册）
  → 内核按调用号查 syscall 表，调用对应服务例程（如 sys_read）
  → 执行完，返回结果，执行 sysret/iret 回到用户态
```

```c
/* 用内联汇编直接做一次 write 系统调用（Linux x86-64） */
long syscall_write(int fd, const char *buf, long n) {
    long ret;
    __asm__ volatile (
        "syscall"
        : "=a"(ret)
        : "a"(1),            /* RAX = 1 = sys_write */
          "D"(fd), "S"(buf), "d"(n)  /* RDI, RSI, RDX */
        : "rcx", "r11", "memory"
    );
    return ret;
}
```

> **为什么不直接 `jmp` 进内核？** 那是特权切换，CPU 不会允许低特权代码随便跳到高特权段；`syscall` 是 CPU 提供的**受控入口**，硬件自动提权并切栈，安全且快。

## 五、中断处理：上半部与下半部

ISR 里若做太多事（如处理一个网络包），会**阻塞其他中断、抬高延迟**。故经典拆分：

- **上半部（Top Half / Hard IRQ）**：只做最紧急的——应答设备、读/写关键寄存器、唤醒下半部。运行在**中断上下文**，**不能睡眠、不能调度**。
- **下半部（Bottom Half）**：把耗时活推迟到可睡眠的上下文做。实现机制：
  - **软中断（SoftIRQ）**：内核静态定义、可在多核并行，用于高吞吐（如网络收包 `NET_RX`）。
  - **tasklet**：基于软中断，同一 tasklet 不会在两核并行，简单常用。
  - **工作队列（workqueue）**：跑在**内核线程**里，**可睡眠**，适合要等、要分配内存的下半部。

> MCU 呼应（见 `02` 第七章、第十章）：RTOS 里 ISR 只做"打标记 + 释放信号量/队列"，真正的业务在任务里处理——这就是"上半部/下半部"思想的极简版。`...FromISR` 系列 API 专门用于 ISR 中安全地唤醒任务。硬规则：**ISR 内不调用会阻塞/睡眠的 API**。

## 六、中断与调度、临界区的关系

- **中断能抢占任务**：硬件中断随时打断当前任务（除非被屏蔽），ISR 跑完若唤醒了更高优先级任务，会在中断返回前触发上下文切换（PendSV 延迟切换，`02` 6.3）。
- **临界区怎么不被中断破坏**：进入临界区临时屏蔽可屏蔽中断（RTOS 用 `BASEPRI` 只挡低优先级，保留高优先级响应）；多核还要配自旋锁防别的核同时进临界区。
- **中断嵌套**：高优先级中断可打断低优先级 ISR（NVIC 支持，尾链/迟滞优化减少开销，`02` 5.2）。

---

## 七、常见坑

1. **ISR 里睡眠/调用会阻塞的 API**：中断上下文不能调度，一睡就崩——务必只用 `...FromISR` 与自旋安全的原语（`02` 10.2）。
2. **中断处理太久**：大段逻辑放 ISR，拖高所有中断延迟，实时性崩；应用"上半部/下半部"拆分。
3. **忘记发 EOI**：中断控制器不解除，该中断再也不来（或一直嵌套）。
4. **竞争：ISR 与任务共享变量无保护**：用 `volatile` 不够（只防编译器优化，不保证原子/内存序），需关中断或小锁/原子。
5. **系统调用号/参数约定写错**：用户态与内核约定的寄存器不一致，得到错误结果或 `ENOSYS`。
6. **在关中断时调可能睡眠的函数**：死锁/崩溃。
7. **多核共享变量只用单核思维**：忘了别的核也在跑，需自旋锁 + 内存屏障。

## 八、面试要点

1. **中断、异常、系统调用的区别？** 中断异步来自硬件；异常同步来自指令执行（故障/陷阱/终止）；系统调用是程序主动用 `syscall` 陷入内核（自愿陷阱）。
2. **系统调用到底发生了什么？** 用户态放号与参 → 执行 `syscall` 提权切内核栈 → 查 syscall 表 → 内核服务例程执行 → 返回用户态。
3. **为什么不能直接 jmp 进内核？** 特权隔离；`syscall` 是 CPU 提供的受控提权入口。
4. **上半部/下半部为什么拆分？** ISR 不能久占、不能睡；耗时活推迟到可睡眠的下半部（软中断/tasklet/workqueue）。
5. **中断上下文为什么不能睡眠？** 没有"进程"上下文可调度，睡眠会导致系统卡死。
6. **Cortex-M 的 PendSV 为何用于切换？** PendSV 是最低优先级异常，把上下文切换延迟到"所有高优先级（含 ISR）都处理完"再做，避免打断紧急 ISR（见 `02` 5.4）。
7. **临界区怎么保护不被中断？** 屏蔽可屏蔽中断（RTOS 用 BASEPRI 精准屏蔽），多核再加自旋锁。
8. **尾链（Tail-Chaining）是什么？** NVIC 优化：连续两个异常返回后立刻进下一个，不再完整出/入栈，省开销。
