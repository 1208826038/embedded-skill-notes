# 跨团队协同与需求管理：把 SOR 变成代码

## 一、"需求变了，但没人告诉我们"

有个项目至今让我记忆犹新。系统工程师在邮件里口头提了一句"这个节点要支持 29 位扩展帧，顺带把诊断会话超时改成 500ms"，软件这边没当回事，照着旧需求写了 11 位标准帧、超时 1000ms。等到整车联调，网关路由发现 ID 对不上、诊断仪会话老掉线，来回扯皮两周才定位到"需求没进基线"。那两周里，硬件在等软件、测试在等硬件、项目节点一天天逼近。

这件事的代价教会我一条铁律：**变更成本随项目阶段指数上升**。需求阶段改一行字，成本近乎为零；到量产前改，可能要重做驱动、重测、重新过准入。所以跨团队协同的第一要务，不是"写代码快"，而是**把需求钉死成书面基线，再让它流进代码**。

## 二、SOR：需求的书面基线

在汽车电子里，客户需求通常以 **SOR（Statement of Requirements，需求声明书）** 的形式输入。它不是一句"要支持 CAN FD"，而是逐条、可验证、可追溯的条目。以 BMS 相关需求为例，SOR 会明确：

- **通信需求**：支持 CAN 2.0B（11/29 位）、CAN FD（数据段 ≤8Mbps）、报文清单与周期、信号精度。
- **功能安全需求**：某功能定级 ASIL D，要求空间隔离 + 端到端保护，诊断覆盖率 SPFM ≥ 99%。
- **实时性需求**：某控制任务周期 10ms，WCET < 8ms，抖动 < 1ms。
- **功耗需求**：整车下电后 BMS 静态电流 ≤ 某 μA 级指标，唤醒源与延迟要求。

SOR 的关键不在"写了什么"，而在**它成为所有团队的共同契约与变更闸门**。任何修改都必须走变更流程，更新 SOR，并同步影响分析。

更进一步的工程实践是把 SOR 和**需求追溯矩阵（Traceability Matrix）**绑定：每条 SOR 条目 → 对应设计 → 对应代码模块 → 对应测试用例。这样"我们到底覆盖了客户哪些需求"随时可查，也是 ISO 26262 / ASPICE 审核的硬指标。

## 三、把 SOR 变成代码：需求落地的链路

需求不会自动变成正确的代码，中间需要一条可追踪的链路：

```
客户 SOR
  │  (评审、拆解)
  ▼
系统需求 / 软件需求规格（SRS）
  │  (架构设计)
  ▼
AUTOSAR 配置 / MCAL 参数 / 通信矩阵(DBC)
  │  (代码生成 + 手写驱动)
  ▼
可运行固件
  │  (测试用例反向映射)
  ▼
需求覆盖率报告
```

以"支持 CAN FD"为例：SOR 写"数据段 ≤8Mbps"→ 系统定"仲裁段 500k、数据段 2M"→ DBC 与通信栈按 FD 配置 → 代码用标定变量动态设 FDF/BRS 标志（见工具链自动化篇）→ 测试用例验证 FD 帧收发。整条链每一环都能指回 SOR 的那一行。

我牵头过客户需求输入评审会，核心动作就是**逐条过 SOR、把模糊表述钉成可验证数字、形成书面基线**，避免"到时候再说"埋雷。

## 四、供应商协同：芯片平台准入评审

除了内部跨团队，汽车电子还有大量**供应商/原厂协同**，最典型的是芯片平台准入评审——这也是我主导过的工作。准入不是"原厂说能用在车规就行"，而是拉通系统/硬件/软件/测试多方，从四个维度打分：

1. **技术可行性**：寄存器/外设/功耗是否满足，MCAL 能否移植，是否要 workaround。
2. **质量体系**：是否具备 IATF 16949，能否提供 PPAP（生产件批准程序，含设计记录、过程能力、测试报告等 18 项）。
3. **功能安全支持**：是否提供 ASIL 支持能力、安全手册、故障模式数据。
4. **供货风险**：产能、生命周期、长期供货、是否有替代料。

评审输出**准入结论 + 风险清单**。对"原厂说不支持某特性"的情况，处理方式有四种：评估替代方案、找 workaround、换料号、或把需求推入原厂路线图——但绝不能在没评估的情况下硬上。

## 五、一条 SOR 如何追到一行代码：可追溯性实例

"可追溯"不是口号，要落到一条具体链路上。以 BMS 一条真实风格的需求为例：

> **SOR-142**：单体电压采样精度 ≤ ±2mV，且该采样链路定级 ASIL C。

它可以一路追下去：

```
SOR-142（客户需求）
  → SRS-318 软件需求："ADC 采样周期须 ≥ 建立时间；启用内部 offset/gain 校准"
    → 设计 DDR-077："高压采样采用 MUX+ADC+DMA，DMA buffer 32 字节对齐"
      → 代码 CellMon_Drv.c : Adc_SampleCellVoltage()
         链接脚本 .dma_buf (NOLOAD) ALIGN(32)
      → 测试 TC-553："注入标准电压源，验证 6 节采样误差 ≤ ±2mV"
```

这条链**正向**证明"需求被覆盖了"，**反向**也成立——任何一段代码/测试都能指回某条 SOR，避免"写了没人要的功能"或"漏了某条需求"。这正是 ASPICE 评估里需求管理成熟度的核心：不仅要有需求，还要有**双向追溯矩阵**与一致性。

**变更如何走**：提出变更 → **影响分析**（代码/配置/测试/时序 WCET/功能安全四维度）→ 更新 SOR 与追溯矩阵 → 重测 → 关闭。我见过最贵的教训，就是某人改了一个发送周期，连带缓冲区大小、WCET、看门狗窗口全要重算，却只改了一处——影响分析清单就是为了防止这种"改一点、炸一片"。

**供应商风险清单**也该结构化，例如准入评审输出的风险项：① 技术可行性风险（某外设需 workaround）；② 供货风险（单一来源、无替代料）；③ 质量风险（PPAP 提交延迟）；④ 功能安全风险（原厂未提供安全手册）。每条风险带责任人、缓解措施、闭环日期——这才是"拉通多方"的评审产出，而不是一页"原则同意"。

## 六、常见坑与协同手段

**坑 1：需求只停在口头/邮件，没进 SOR 基线**
现象：联调才发现和理解不一致，返工扯皮。
手段：所有需求变更必须书面化进 SOR，走变更审批；建立单一真相源。

**坑 2：需求与代码/测试脱节，追溯断链**
现象：审核时答不出"这条需求对应哪段代码、哪个测试"。
手段：维护需求追溯矩阵，需求→设计→代码→测试逐层可追；导入 ALM/需求管理工具。

**坑 3：供应商承诺与实测不符**
现象：原厂说"完全兼容"，上板就出时序问题（见国产替代篇）。
手段：准入阶段就要做原型验证与基准波形比对，把"宣称"变成"实测证据"。

**坑 4：变更影响评估不充分**
现象：改一个周期，连带触发缓冲区大小、WCET、看门狗窗口全要重算，却只改了一处。
手段：变更流程强制做影响分析（代码/配置/测试/时序/安全），更新 SOR 与矩阵后重测。

**协同手段清单**：① 定期需求评审会，逐条确认；② SOR + 追溯矩阵双基线；③ 供应商技术对齐会（原厂/代理商），留存会议纪要；④ 变更走流程，影响分析留痕；⑤ 用 DBC/配置工具把需求"编译"进代码，减少人工传递误差；⑥ DBC 本身就是跨团队契约——系统、软件、测试、甚至产线诊断都按它编解码，把它当"接口文档"统一版本管理，能从源头消弭"你说的是哪版通信矩阵"这类扯皮；⑦ 引入 ALM（应用生命周期管理）工具而不是用散落邮件管理需求，让追溯矩阵自动生成、审计算法可追溯，是规模项目从"人治"走向"流程"的关键一跃。

## 七、面试高频要点

- **SOR 是什么，为什么重要？** Statement of Requirements，书面需求基线；源头钉死需求，避免后期变更指数级返工。
- **怎么保证需求不丢、可追溯？** 需求追溯矩阵，需求→设计→代码→测试逐层映射；是 ISO 26262/ASPICE 审核基础。
- **原厂说"不支持某特性"怎么处理？** 评估替代方案 / workaround / 换料号 / 推需求进路线图，不盲上。
- **芯片准入评审看哪几个维度？** 技术可行性、质量体系（IATF 16949 / PPAP）、功能安全支持、供货风险。
- **变更为什么越早越好？** 变更成本随项目阶段指数上升，需求期改字 vs 量产前改驱动，代价天差地别。
