# 操作系统进阶（三）· 同步、互斥与死锁

> 上一章讲"多个执行流怎么被调度"，本章讲"它们怎么安全地协作"。只要多个线程/进程**共享可变状态**，就必然有竞态（Race）。本文从临界区讲起，逐一拆解互斥量、信号量、管程、自旋锁、无锁，再深入死锁的四大条件、银行家算法、检测与恢复，以及活锁/饥饿。内容直接呼应 `02-rtos-tuning.md` 第七章（RTOS IPC）与第八章（死锁），把"工程 API"背后的理论补全。

---

## 一、竞态条件与临界区

### 1.1 竞态（Race Condition）

当多个执行流**并发**访问同一共享变量，且**最终结果取决于它们的执行顺序**时，就出现竞态。经典例子（接 `o01` 的 `shared_counter++`）：

```
线程A: 读 counter=5 → 计算 5+1=6 → 写回
线程B: 读 counter=5 → 计算 5+1=6 → 写回   （与 A 交错，本应得 7，实际得 6）
```

`counter++` 编译后是"读-改-写"三条指令，不是原子的。多核下两个线程可能同时读到旧的 5。

### 1.2 临界区（Critical Section）

访问共享资源的代码段叫临界区。要保证**互斥（Mutual Exclusion）**：任一时刻最多一个执行流在临界区内。同步机制的目标就是安全、高效、公平地把执行流放进/放出临界区。

---

## 二、互斥的软件与硬件基础

### 2.1 禁用中断（最朴素）

单处理器上，"进入临界区前关中断、出来再开"可阻止抢占，实现互斥。但：
- 多核上无效（别的核照样跑）。
- 关中断太久会丢外部事件、影响实时性。
- 用户态不允许关中断（特权操作）。
RTOS 的临界区用的是**屏蔽部分优先级中断（BASEPRI）**而非全关，正是这一思想的精巧版（见 `02` 第六章 6.2）。

### 2.2 硬件原子指令

CPU 提供原子原语让"读-改-写"一气呵成：
- **Test-And-Set**：原子地"读旧值并置 1"。
- **Compare-And-Swap (CAS)**：原子地"若当前值==预期则换成新值，返回旧值"——无锁编程的基石。
- **Fetch-And-Add**：原子自增，直接用于计数器。

```c
/* CAS 自旋锁的极简实现（示意） */
int lock = 0;
while (!CAS(&lock, 0, 1)) { /* 自旋直到抢到 */ }
/* 临界区 */
lock = 0;  /* 释放 */
```

## 三、锁：互斥量（Mutex）

### 3.1 互斥量语义

Mutex 是"带所有权"的锁：谁 `lock` 谁必须 `unlock`，且**不能递归加同一把锁**（否则自死锁）。它解决了临界区互斥，且获取不到时线程**阻塞**（睡眠，让出 CPU），不像自旋锁空转。

### 3.2 优先级反转（与 RTOS 呼应）

经典陷阱（详见 `02` 第三章 3.4）：低优先级任务 L 持锁，中优先级 M 抢占 L，高优先级 H 等锁 → H 竟被 M 间接阻塞！解法：
- **优先级继承（PIP）**：L 持锁时临时提升到 H 的优先级，避免 M 插队；释放后恢复。只解反转，不解死锁。
- **优先级天花板（Priority Ceiling）**：锁配一个天花板优先级（= 所有会用这把锁的任务的最高优先级），持锁即顶到天花板。能同时抑制反转与死锁、可静态分析——AUTOSAR `OsResource` 采用此方案（见 `b09`/`02` 第十五章）。

## 四、信号量（Semaphore）

Dijkstra 提出，是整数变量 + P（wait）/ V（signal）两个原子操作：
- **二值信号量**（0/1）：功能等同互斥量（但无所有权、可跨线程释放）。
- **计数信号量**：资源池计数，如"5 个连接槽"，P 减一（为 0 则阻塞），V 加一。

```c
sem_t sem;  sem_init(&sem, 0, 1);   /* 初值 1 = 二值 */
sem_wait(&sem);    /* P：进入临界区 */
/* 临界区 */
sem_post(&sem);    /* V：离开 */
```

> 对比 `02` 第七章：RTOS 的二值/计数信号量、`xSemaphoreTake/ Give` 就是这个抽象在嵌入式上的实现；而**信号量不解决优先级反转**，需要带优先级继承协议的"互斥量"（FreeRTOS 的 `Mutex`/`Recursive Mutex`）。

## 五、管程（Monitor）与条件变量

### 5.1 管程：把锁和条件封装成对象

管程是**高级同步构造**：一个对象内部封装了共享数据 + 一把隐式互斥锁 + 若干**条件变量（Condition Variable）**。进入管程方法自动加锁，出来自动解锁，程序员不用手动配锁。Java 的 `synchronized`、C# 的 `lock`、Go 的 `sync.Mutex`+`Cond`、Python 的 `with Lock` 都是管程思想的落地。

### 5.2 条件变量（Condition Variable）

条件变量解决"等某个条件成立"——光有互斥量只能互斥，不能"等待条件"。条件变量配 `wait`（释放锁并睡，被唤醒后重新拿锁）与 `signal/broadcast`（唤醒一个或多个等待者）。

```java
class BoundedBuffer {
    private final Object[] buf = new Object[10];
    private int count = 0;
    private final Object lock = new Object();
    void put(Object x) throws InterruptedException {
        synchronized (lock) {
            while (count == buf.length) lock.wait();  /* 满则等 */
            buf[count++] = x;
            lock.notify();                            /* 唤醒可能等待的取者 */
        }
    }
    Object take() throws InterruptedException {
        synchronized (lock) {
            while (count == 0) lock.wait();          /* 空则等 */
            Object x = buf[--count];
            lock.notify();
            return x;
        }
    }
}
```

> 关键细节：**用 `while` 而非 `if` 检查条件**（防止虚假唤醒/唤醒后条件已变），`notify` 前必须持有锁。这是并发 Bug 的高发区。

## 六、自旋锁 vs 阻塞锁 / 无锁

### 6.1 自旋锁（Spinlock）

获取不到时**忙等**（占着 CPU 空转），不睡眠。适用：**临界区极短 + 多核 + 不允许睡眠的上下文（如中断处理、内核自旋锁持有期间）**。单核上自旋锁无意义（持有者无法跑），故单核 RTOS 常用"关中断"代替。

### 6.2 无锁（Lock-Free）

基于 CAS 等原子指令，保证"至少一个线程总在前进"，无需传统锁：
- **Lock-Free**：系统整体总有进展。
- **Wait-Free**：每个线程都能在有限步内完成（更强）。
常用于高并发队列、引用计数。代价：ABA 问题（值从 A→B→A，CAS 误判未变，需用带版本号的"双字 CAS"或 Hazard Pointer 解决）。

## 七、死锁（Deadlock）

### 7.1 四大必要条件（Coffman）

死锁**同时**满足以下四条才发生：
1. **互斥（Mutual Exclusion）**：资源不可共享。
2. **占有并等待（Hold and Wait）**：持有一份资源的同时还申请别的。
3. **不可抢占（No Preemption）**：资源只能自愿释放。
4. **循环等待（Circular Wait）**：A 等 B 的、B 等 A 的资源，形成环。

**破坏任一即可预防死锁**。

### 7.2 预防（破坏条件）

| 破坏哪条 | 做法 | 代价 |
| --- | --- | --- |
| 互斥 | 用可共享资源（大多不可行） | 受限 |
| 占有并等待 | **一次性申请所有资源**（不够就全部不拿） | 资源利用率低、可能饥饿 |
| 不可抢占 | 申请不到时**释放已持有的**（回滚重试） | 实现复杂 |
| 循环等待 | **资源按全局固定序号申请**（只能升序拿） | 需编号、可能低效 |

> RTOS 呼应：`02-rtos-tuning.md` 第八章"资源分级法"就是**循环等待的预防**——给每把锁编全局序号，任务只能按升序申请，从根上杜绝环。

### 7.3 避免：银行家算法（Banker's Algorithm）

**动态**判断"这次分配后系统是否仍处于安全状态"（存在一个让所有进程都能跑完的分配序列）。若是才批准，否则让请求者等待。

```
可用资源 Available = [3,3,2]
进程最大需求 Max、已分配 Allocation、需求 Need=Max-Alloc
安全性检查：能否找到一个推进序列，使每个进程 Need ≤ Available，跑完释放其 Allocation
```

银行家算法要求**预知每个进程的最大需求**且进程数固定，现实中（尤其通用 OS）很少直接用，但它是"避免死锁"的理论基准，面试必考。

### 7.4 检测与恢复

- **检测**：维护资源分配图，周期性检测是否出现环（有环即死锁，单资源类型；多资源类型用类似银行家的矩阵算法）。
- **恢复**：① 终止进程（杀掉死锁环里一个或多个）；② 资源抢占（剥夺并回滚）。代价都大，多用于检测而非预防的场景（如数据库）。

## 八、活锁与饥饿

- **活锁（Livelock）**：进程没死锁（在运行），但一直在"礼貌地互相让"形成无限循环，谁也前进不了（如两人走廊相遇反复侧身让路）。解决：加随机退避。
- **饥饿（Starvation）**：某进程长期拿不到资源（如一直有更高优先级者插队）。解决：老化（提升等待久的优先级，见 `o02` 5.1）。

## 九、常见坑

1. **在中断上下文用会睡眠的锁**：中断里不能睡眠，用了 mutex 会死机——中断内只能用自旋锁或 `...FromISR` 原语（见 `02` 第十章）。
2. **条件变量用 if 而非 while**：虚假唤醒后条件其实没满足，直接往下走破坏不变量。
3. **忘记释放锁 / 异常路径漏 unlock**：用 RAII（`lock_guard`）或 `try/finally` 保证释放。
4. **重复加同一把非递归锁**：自死锁，用递归锁（`Recursive Mutex`）或重构。
5. **死锁靠"加超时"掩盖**：`try_lock` 超时只是把死锁变活锁/重试风暴，根因（加锁顺序）没解决。
6. **ABA 问题**：CAS 无锁队列里值来回变导致误判，用版本号/双字 CAS。
7. **锁粒度太粗**：整个函数一把大锁，并发退化为串行；太细又有死锁/性能成本，需权衡。

## 十、面试要点

1. **临界区与竞态？** 共享可变状态 + 交错访问导致结果依赖顺序，即竞态；临界区是访问共享资源的代码段。
2. **互斥量与二值信号量的区别？** 互斥量有所有权（谁锁谁解、可防优先级反转），二值信号量无所有权、可跨线程释放。
3. **条件变量为什么配 while？** 防止虚假唤醒后条件不满足仍往下执行，破坏不变量。
4. **死锁四条件？如何破坏？** 互斥/占有等待/不可抢占/循环等待；按固定全局序申请资源破循环等待（资源分级法）。
5. **银行家算法做什么？** 分配前判断系统是否安全（存在完成序列），避免死锁，但需预知最大需求。
6. **自旋锁适用场景？** 多核、临界区极短、不可睡眠的上下文（中断）；单核无意义。
7. **活锁 vs 死锁？** 死锁是互相等待静止；活锁在动但都无进展（互相礼让），靠随机退避解。
8. **优先级反转怎么解决？** 优先级继承或天花板协议（AUTOSAR 用天花板）。
