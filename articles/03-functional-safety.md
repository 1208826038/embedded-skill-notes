# 功能安全 ISO 26262：从 ASIL 等级到安全机制落地

## 一、一起"差点"的安全事故

某 BMS 项目在 HIL（硬件在环）台架上做故障注入测试：故意让一个 QM（非安全相关）等级的通信任务跑飞，去非法写入一块本应属于 ASIL D 安全任务的共享内存。预期结果是 MPU 拦截这次越权写、系统进入安全状态。但初版实现里，出于"省事"，两个任务共用了同一块 RAM 且没有 MPU 分区——结果越权写成功，安全任务的电芯电压判定被污染，系统没有按预期断高压。

这不是小概率的假设。真实产线上，一个第三方算法库溢出、一个未初始化的指针、一次 DMA 写错地址，都可能踩坏安全关键数据。ISO 26262 要解决的，正是"电子电气系统失效不能危及人身安全"。本篇从 ASIL 等级讲起，一直落到 MPU 隔离、诊断覆盖率这些真正能写进代码的动作。

## 二、ASIL 等级：风险怎么被量化

ISO 26262 用三个维度推导 ASIL（汽车安全完整性等级）：

- **S（Severity，严重度）**：失效后果对人的伤害程度；
- **E（Exposure，暴露概率）**：危险工况发生的可能性；
- **C（Controllability，可控性）**：驾驶员能否避免伤害。

三者组合，把风险分成 **QM、A、B、C、D**。A 到 D 风险递减，**D 最严格**，其随机硬件失效的可接受概率约需低于 `10^-8 / h`（即每运行 1 亿小时平均不到 1 次危险失效）。QM 是最低要求，表示"非安全相关"。

**类比**：ASIL 就像驾照考试难度。QM 是骑共享单车，A 是开小电驴，D 是开危化品运输车——出事代价越大，对司机、车辆、流程的要求越苛刻。ASIL D 相比 B，需要更高的**诊断覆盖率（DC）**、更多的独立验证、更严格的文档与测试，工作量往往是数倍。

## 三、Freedom From Interference：低不能干扰高

功能安全的灵魂概念是 **FFI（Freedom From Interference，免于干扰）**：低 ASIL 元素不得影响高 ASIL 元素的正常运行。它有三个维度的隔离：

1. **空间隔离**：内存分区，低 ASIL 任务碰不到高 ASIL 任务的数据（MPU 实现）。
2. **时间隔离**：调度保证高 ASIL 任务有确定的时间窗，不被低 ASIL 任务拖延。
3. **通信隔离**：跨模块/跨核通信靠端到端保护（E2E Profile：CRC + 计数器 + 超时）。

回到开头那起事故，我们最终的修复方案就是一整套隔离机制组合：**MPU 分区 + 编译期内存分配（链接脚本固定各模块地址）+ 看门狗/ECC + 端到端通信保护**。

## 四、从 MPU 到 ASIL D：单核也能做空间隔离

很多人误以为"单核 MCU 做不到 ASIL D 的空间隔离，必须上多核或多 OS"。其实不然。在没有 MMU 的单核车规 MCU 上，可以靠 **MPU 分区 + 编译期固定内存布局 + 栈/数据分离** 实现空间隔离。

具体落法：

1. 在链接脚本里，把 ASIL D 任务的代码、数据、栈分配到固定地址区间；
2. 用 MPU 给这块区域配独立权限（如 RX 代码、RW 数据，其他任务不可写）；
3. 给 QM 任务配另一块 MPU 区域，禁止它访问 ASIL 区域；
4. 一旦 QM 任务越权访问，硬件立刻触发 MemManage Fault（HardFault 子类），软件在 Fault Handler 里进入安全状态（如断高压、亮故障灯）。

```c
/* 为 ASIL D 安全任务配置独立 MPU 保护区（示意） */
void MPU_Config_ASIL_D_Region(void) {
    MPU->CTRL = 0;                                  /* 先关 MPU 再改 */
    MPU->RBAR = (SAFE_RAM_BASE & 0xFFFFFFE0u)
              | MPU_RBAR_VALID_Msk | (REGION_ASIL << MPU_RBAR_REGION_Pos);
    MPU->RASR = MPU_RASR_XN(0)                     /* 可执行 */
              | MPU_RASR_AP(0x3)                   /* 特权+用户可读写 */
              | MPU_RASR_SIZE(13)                  /* 2^(13+1)=8KB */
              | MPU_RASR_ENABLE_Msk;
    /* 同时配一个 QM 区域，AP=只读，禁止写入 SAFE 区 */
    MPU->CTRL = MPU_CTRL_ENABLE_Msk | MPU_CTRL_PRIVDEFENA_Msk;
    __DSB(); __ISB();
}
```

注意 `MPU_CTRL_PRIVDEFENA`：允许特权模式下的默认背景区，但用户模式必须严格走各区域权限——这正好把"特权底层驱动"与"非特权应用"区分开。

## 五、诊断覆盖率、SPFM 与 LFM

功能安全不是"加个看门狗"就算完。ISO 26262 对硬件架构有量化指标，以 ASIL D 为例，**单点故障度量 SPFM（Single-Point Fault Metric）需 ≥ 99%**，**潜在故障度量 LFM（Latent Fault Metric）也需达标**。

- **SPFM**：衡量系统能诊断出"单点故障"的比例。单点故障指一个故障直接引发危险失效、且无冗余可覆盖。提高 SPFM 的手段：ECC（单 bit 纠错）、MPU 越权检测、总线 CRC、电源监控。
- **LFM**：衡量系统能发现"潜在故障"（已发生但暂未酿成危险、需要多条件叠加才出事）的比例。手段：周期性自检、BIST（内建自测试）、诊断任务定期扫描。

**类比**：SPFM 像你家门锁——小偷一撬就被发现（诊断快）；LFM 像藏在墙里的老化电线——平时没事，得定期巡检才防得住（诊断慢但必须做）。两者都达标，才算"安全"。

## 六、流程要求：可追溯与测试

功能安全 50% 是工程、50% 是流程：

- **需求可追溯**：建立双向追溯矩阵，从安全需求 → 设计 → 代码 → 测试都能对上；
- **单元测试**：要求 MC/DC 覆盖率（修正条件/判定覆盖），比普通分支覆盖更严；
- **静态分析**：强制 MISRA C 规则集，消除未定义行为；
- **故障注入测试**：主动注入 RAM/寄存器错误，验证 ECC 是否真触发、WDT 是否真复位；
- **安全分析**：FMEA（故障模式影响分析）、FTA（故障树分析）、DFA（相关失效分析）。

## 七、常见坑与调试手段

1. **MPU 区域重叠或对齐错误**：MPU 区域基址必须按 `2^(SIZE+1)` 对齐，配置错会导致整片内存属性异常。调试：读出 `RBAR/RASR` 比对对齐要求，用调试器访问各地址验证属性。
2. **只在"配过 MPU"就声称懂功能安全**：面试/审核最忌讳。正确姿态是讲清 ASIL 推导、FFI 三隔离、诊断覆盖率、追溯性，而非只说"我开了 MPU"。
3. **ECC 双 bit 错误未进入安全状态**：单 bit 自动纠、双 bit 报错，但若错误处理函数只打日志不断高压，等于没保护。调试：故障注入双 bit 错误，确认系统按预期进入安全状态而非继续运行。
4. **E2E 保护缺失导致跨核误判**：ASIL 任务信任了来自 QM 任务的脏数据。调试：在通信路径加 E2E 校验，注入错误序列验证接收端丢弃并告警。

## 八、安全机制与故障注入实证

功能安全最忌"配了就行"。ISO 26262 要求用**故障注入**实证诊断覆盖率真的达标，而非纸面宣称：

- **RAM 位翻转注入**：通过 MBIST 或软件翻转某 bit，验证 ECC 是否单 bit 自动纠、双 bit 正确报错并进入安全状态；
- **寄存器错误注入**：破坏关键控制寄存器值，验证看门狗/监控逻辑是否检测并复位；
- **通信故障注入**：拉低电压、断线、注入错误 CRC，验证端到端保护是否丢弃脏数据、系统是否降级而非失控；
- **时钟失效注入**：停掉或抖动主时钟，验证时钟监控（如窗口看门狗时基）是否报警。

这些注入测试的数据，正是 FFI 与诊断覆盖率达标的**证据链**。审核员要看的不是"我设计了 MPU"，而是"我注入了 XX 种故障、系统全部按预期进入安全状态"的测试报告。这也就是为什么开头那起 HIL 事故里，我们不仅要修代码，还要补一套完整的故障注入用例回归。

## 九、安全机制的两大分类：预防与检测

落地安全机制时，要分清两类思路：**预防性机制**让故障不发生或隔离（如 MPU 空间隔离、双核锁步 Lockstep、冗余电源），**检测性机制**在故障发生后及时发现（如 ECC、CRC、看门狗、电源监控、诊断任务）。ISO 26262 的 SPFM/LFM 指标，考核的正是检测性机制的覆盖率——你有多少比例的失效能被"看见"。

以双核锁步（Cortex-R 典型特性）为例：两个核心跑同一份代码、同一输入，比较器实时比对其输出，一旦不一致立即报错。这是预防性（硬件冗余）与检测性（比较器）的结合，对 ASIL D 这类极高要求场景几乎是标配。理解"预防 vs 检测"的区分，能帮你在做安全分析（FMEA/FTA）时系统地不漏项。

## 十、面试高频要点

- **ASIL D 和 B 工作量差多少？** D 需更高诊断覆盖率、更多独立验证、更严文档与测试，工作量数倍。
- **单核 MCU 怎么做到 ASIL D 的空间隔离？** MPU 分区 + 编译期固定内存布局 + 栈/数据分离。
- **什么是 FFI？** 低 ASIL 不能干扰高 ASIL 元素的运行，靠空间/时间/通信隔离保证。
- **什么是 SPFM / LFM？** SPFM 衡量单点故障诊断覆盖率（ASIL D ≥ 99%），LFM 衡量潜在故障诊断覆盖率。
- **怎么证明你"懂"功能安全而不只是配过 MPU？** 讲清 ASIL 推导、FFI 三隔离、诊断覆盖率、追溯性，而非只说"开了 MPU"。
